## Ordered remaining tasks and acceptance

These are implementation task cards, not claims that changes have already shipped. F-01 through F-04 can start without a backend contract change. Prioritize a real exam/receipt integration as soon as the backend is available; do not use further demo polish to postpone it (master plan section 13.3).

### F-01: Collapsible question navigator

Owner: frontend. Add an accessible expand/collapse control to the official runner, retaining current-question and answered/unanswered information. Collapsing must not change answers or prevent Previous/Next navigation. Verify keyboard control, announced expanded state, 360px layout and a 200-question paper. Reopen navigation without losing position or saved selections. No API changes.

### F-02: Preparation progress

Owner: frontend. Expose real phases from `preparePaper`: verify eligibility, register/recover attempt, download, checksum, local save and offline-shell check. Show the failing phase and retry guidance. Use indeterminate progress when the transport has no byte total; never manufacture a percentage. Ready must require every production check. Verify cancellation, corrupt package, quota failure, shell failure and retry without duplicate attempts. No backend endpoint is needed for local phase feedback.

### F-03: Scheduling clock and actionable validation

Owner: frontend. Show current EAT derived from a server sample plus monotonic elapsed time; the current form compares against the original detail response indefinitely. Separate invalid format, past preparation and too-early results errors beside their fields; refresh/revalidate stale data. Keep the confirmation reset when schedule inputs change. Verify Pacific/EAT displays, crossing midnight, time passing while the form is open, reschedule cutoff and backend rejection. The server remains timing authority. Accommodation-aware preview depends on F-05.

### F-04: Cold-reload recovery entry

Owner: frontend. When a cold reload cannot restore the session, show explicit reconnect/revalidate guidance and warn against clearing site storage. Do not expose saved answers or identify another account before authentication. After the same user signs in, return to the intended attempt, recover evidence and require online time/device revalidation before editing. Verify an actual built app/service worker with offline reload, reconnect, expired login, a different user, pending final payload and a submitted receipt. A runner-unit test alone is insufficient.

### F-05: Accommodation configuration and contract

Owner: frontend/project contract owner, then backend. Define a concrete admin-authorized path for assigning and inspecting extra minutes before the roster is frozen. Existing BE-04 assumes authorized accommodations already exist but provides neither their creation payload nor a UI. Issue executable schemas and the backend addendum before implementation; include school/student/session scope, revisions, audit reason, idempotency, freeze boundary and planned-results validation against the latest deadline. Display common end separately from individual/latest deadlines. Verify an accommodated student, a late join, an unauthorized/stale edit, schedule changes and refusal after the cutoff. Do not silently default an approved accommodation to zero or let backend invent an incompatible interface.

### F-06: Verified preparation acknowledgement in monitoring

Owner: frontend/project contract owner, then backend. Define a version/generation-bound acknowledgement after checksum, local write and production shell verification. The administrator needs a separate ready count; current preparing must remain truthful. Issue schemas, acknowledgement/replay rules and monitor response changes before wiring them. Invalidate readiness when its relevant version/device changes. Clearly label it as last reported readiness, not proof of continuing connectivity or storage availability. Verify failed preparation is never counted ready and monitor reads never create readiness. Do not infer ready from attempt creation, package response or last contact.

### F-07: Browser, phone and integrated acceptance

Owner: frontend with backend staging support. Replace the echo-only e2e command with executable browser journeys and CI support. Keep demo tests explicitly separate from real-API acceptance. Cover all roles, import/return/review/approval, scheduling, interrupted exam/receipt, recovery, publication, exports and practice. Include two schools, multiple students, 1/2/2/4 ties, status rows, the section 18 topic example and 60/80/70 practice scores producing best 80. Verify all student routes at 360px, keyboard/focus states, a real lower-memory Android device, offline/reload/session expiry and production shell updates. Record exact build/API revisions, commands, devices, results and unresolved failures; no placeholder passes.

### F-08: Safe retention and cleanup

Owner: product/school retention decision plus frontend/backend. Record the agreed recovery/retention period before implementing deletion. Define which server-confirmed resolutions permit removal and how active tabs/assets are protected. Test that pending, disputed, unknown-outcome and unresolved recovery records survive; expire only eligible resolved data and unused shell versions. Ordinary logout/401 must never become a blanket deletion operation. This is not permission to delete existing student evidence.

### F-09: Deployment and handover evidence

Owner: frontend plus backend/hosting owner. Create `docs/deploy.md` for the actual supported host/runtime, frontend route fallback, credentialed API configuration, HTTPS, public build variables, private secret boundaries, tested artifact identity, smoke tests, rollback and safe service-worker updates. Backend supplies exact startup/migration/restart and independent backup/restore evidence. Validate a production build with mocks off, login, preparation and one real committed receipt. Record capacity approval separately from functional acceptance.
