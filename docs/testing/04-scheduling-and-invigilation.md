# 4. Approval, calendars, scheduling and invigilators

[Testing home](README.md) · Next: [Student exam](05-student-exam.md)

Use a submitted paper, school administrator and separate teacher/invigilator accounts. Plan several short sittings with enough time for each scenario. Do not change the computer clock during a real local sitting.

1. **Approval queue.** Search/filter by teacher, subject, grade/class and submission dates. Expect only matches; pending papers are ordered by submission, oldest first. Approved/returned views retain their grade organization. Review the question content, return one paper with a reason, then approve a corrected paper.
2. **Approved package.** Approval must not start the exam. Expect scheduling to wait until the approved student package is ready. If preparation stalls, inspect the worker and package guide. Student packages must not contain answer keys/explanations; that requires the technical API/package check too.
3. **Calendar layout.** Open the date picker. Expect a seven-day grid, weekday headings, visible month/year controls and a popup within the screen. Switch Ethiopian/Gregorian and back: the selected instant must remain equivalent. Ethiopian month names are Amharic, numbers are ordinary digits, and clocks use AM/PM EAT.
4. **Timezone.** Compare the saved schedule in another browser timezone. Expect the same EAT time and actual instant. Check 12 AM versus 12 PM deliberately. Verify month/year boundaries using a disposable schedule, without altering the system clock.
5. **Preparation.** Confirm the default is 10 minutes. Save a valid different value; separately test 0. Expect 0 to open preparation at the start, without extra time for downloads. Negative, fractional and over-120 values must be rejected. Preparation and planned result sections should sit beside each other when space permits, stack on phones, and avoid large empty gaps.
6. **Server time and validation.** Wait for automatic school-time loading. Valid scheduling must not require manually pressing Refresh server time first. Invalid start/end/release combinations must give clear feedback. If time verification fails, expect a recoverable error rather than an unexplained permanently disabled button.
7. **Save/reload.** Save the schedule and refresh. Expect the same preparation/start/end/results dates. Repeated submission must not create duplicate sittings. Test conflicting edits in two admin tabs: stale changes must be rejected rather than silently replacing the newer schedule.
8. **Extra time.** Before preparation begins, grant a test student's allowed accommodation. Verify that student's effective deadline and that results/practice wait for the latest submission window. Once the cutoff is reached, late accommodation changes must be rejected. Late joining must not restart any clock.
9. **Create limited staff.** School setup → Accounts → Invigilators: create a non-teaching invigilator. Expect an assistance-only portal, no teacher assignment eligibility and no school management access.
10. **Assign after scheduling.** Under the sitting's saved dates, assign a teacher and a limited invigilator with a reason. Expect only this school's eligible staff and authenticator readiness indicators. Revoke/reassign a disposable assignment and verify the result. An administrator retains school-wide assistance access even without explicit assignment.
11. **Private staff MFA.** On the teacher/invigilator's own assistance page, enter their password, scan the setup QR in Authenticator and confirm the code. Refresh: expect readiness, not the secret again. The administrator/student must not retrieve the staff QR or live codes. Existing factor replacement uses protected recovery.
12. **Ready to run.** Confirm the student is in the frozen sitting roster, has the correct schedule and can reach preparation. Confirm the assigned staff can select this sitting. Test unassigned staff denial on a different sitting before starting the assistance rehearsal.
