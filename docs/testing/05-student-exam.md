# 5. Student download, exam, privacy and assistance

[Testing home](README.md) · Next: [Results and recovery](06-results-and-recovery.md)

Use disposable scheduled attempts, the student's original browser and an assigned staff member signed in on a different profile/device. Use a supported desktop browser for the strict fullscreen flow. A browser without the required fullscreen API cannot start this flow; record that compatibility limitation.

1. **Exam lists.** Check Current, Upcoming, Past and Needs attention views. Expect A–Z ordering within the category and working Load more. Past-result filters distinguish published grades, awaiting results and no grade. Future exams must not unlock early.
2. **Download.** Before download, expect Not started. During preparation, select Download exam. Expect percentage when the response provides a usable length; otherwise an indeterminate indicator. Expect Finishing download during verification. Do not require an invented percentage for unknown lengths. The developer checklist and offline-check instruction should not be shown to the student.
3. **Interrupted download.** On a disposable attempt, interrupt the network during download. Expect a clear error and retry, not false completion. Reconnect and retry. A corrupt or wrong-version package must fail verification; use the technical harness for that case.
4. **Start gate.** Before the common start, questions remain unavailable. At the start, use Start exam and allow fullscreen. Denied fullscreen gives an error and no questions. Starting late never creates a fresh full-duration timer.
5. **Answers/navigation.** Answer several questions, move between them, flag/unflag if available and return. Expect answers to remain and a consistent server-controlled deadline. Changing an answer must update the saved state. Successful submission is shown only after the matching server receipt.
6. **Privacy shield.** Save an answer, switch tabs, leave fullscreen and move the desktop pointer outside the window in separate episodes. Expect questions to hide with an explanatory blackout overlay. After roughly 1.5 seconds and return of focus, Resume restores fullscreen and saved answers without extending time.
7. **Physical keys.** Separately try Windows, Alt, Win+Shift+S, PrintScreen and inspection shortcuts on a disposable exam. Record both whether the shield reacted and whether the OS capture actually contained questions. OS keys may not reach the browser; blackout does not prove capture prevention. Clipboard clearing is permission-dependent: test only with disposable clipboard content. External cameras remain possible.
8. **Watermark/print.** Confirm one watermark and its updating time. In a disposable technical rehearsal, remove the whole watermark node and check self-healing/reporting where supported. Intentional blackout must not create false tamper reports. Print the active exam: questions must not print. Authorized report printing outside the exam should remain usable.
9. **Five-event lock.** Trigger five distinct interruption/resume episodes. Expect the mounted UI to lock and offer Request invigilator help. This is not automatic server suspension/disqualification and is not durable across reload. Never treat an event count as proof of cheating.
10. **Assistance/resume.** Request help. Editing pauses but the deadline continues. On their own device, assigned staff select the sitting, verify the student/request, enter a reason and fresh MFA code, then approve. Back on the student page, wait for refresh and choose Try opening exam again. Expect saved answers and the original deadline. Reject a separate request; it must not grant resume. Staff approval cannot override administrator suspension.
11. **Network loss after unlock.** Disconnect briefly, answer, reconnect and wait for synchronization. Expect local changes preserved and school receipt status to update truthfully. Do not clear browser storage. Reload while offline is not promised: reopening requires online revalidation. Full offline-shell acceptance requires a production build, not just Vite development mode.
12. **Submit/deadline.** Submit normally; verify a receipt and matching final answers. Repeat with a simulated lost response in the technical suite: retry must not produce two submissions. Let another attempt reach its deadline: editing stops and pending submission remains distinguishable from confirmed submission. Unsent evidence must remain available for recovery.
13. **Device replacement.** Rehearse replacement through the authorized device-recovery workflow on a separate attempt. Expect the old generation to lose server authority, retained evidence, and unchanged deadline. Never use arbitrary browser switching as a substitute for approved replacement.
